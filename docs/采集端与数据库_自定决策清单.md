## 一·二、采集端串口阶段（阶段A/B，2026-10 新增）

### D20. 串口接收采用独立线程 + detach

- **我的选择**：`std::thread(UsartRxThread).detach()` 后台常驻收串口，主循环只读 `g_mode`
- **可替代**：在主循环里非阻塞顺带读串口（少一个线程，但主循环被推理占着时指令响应会延迟到下一帧）
- **资料依据**：资料中无板端串口业务代码（demo不用UART），架构为自行设计；串口API用SDK的USART1类（usart.h 原文）
- **你的结论**：＿＿＿＿＿＿

### D21. g_mode 状态定义与 -1 默认模式

- **我的选择**：`atomic<int> g_mode{-1}`；-1=从未收到指令→保持原连续检测逻辑；0/1/2/3 对应协议四条指令
- **可替代**：上电默认进入某个协议模式（如仅播放）——意味着不接串口程序就没输出，调试不便
- **影响**：不接串口也能单机跑，是调试友好性设计
- **你的结论**：＿＿＿＿＿＿

### D22. 接收线程 usleep(20000) 轮询

- **我的选择**：usart.Read 非阻塞（SDK 源码 VMIN=0/VTIME=0），无数据时歇 20ms 再读
- **可替代**：select/poll/epoll 等待串口可读（更优雅但复杂，本场景收益小）；或阻塞读（SDK未提供阻塞配置）
- **影响**：指令响应延迟最多 20ms（相对串口场景可忽略），CPU 空转可控
- **你的结论**：＿＿＿＿＿＿

### D23. 串口打开失败不退出、仅成功时启动接收线程

- **我的选择**：`Open(115200)` 失败只打日志继续跑（单机模式）；线程只在打开成功后启动
- **原因**：失败时 Read 会持续刷 SDK 错误日志，且不接串口不应影响推理功能
- **你的结论**：＿＿＿＿＿＿

### D24. 假设 USART1(/dev/ttyS1) 即 Test-USART 测通的串口 ⚠️待B5验收确认

- **背景**：SDK 的 USART1 类固定打开 /dev/ttyS1；你的回显测试（Test-USART/Test-USART_HEX）源码未见过，无法确认它用的哪个口
- **验证方式**：B5 验收（sscom 发指令看 SSH 打印）通过即假设成立；若打开成功但收不到指令，查板上 `ls /dev/ttyS*` 换口
- **你的结论**：＿＿＿＿＿＿
